Security is more than stopping hackers.

Cloud computing is part of everyday technology, from storing files online to running applications and business systems. But putting something in the cloud does not automatically make it secure.

This guide is made for college students and beginners who already know a little about technology or cloud computing but are new to cloud security. It breaks the topic into smaller sections so the different parts are easier to understand.

01. Understanding Cloud Computing and Cloud Security

Before getting into cloud security, it helps to understand how cloud services are organized. Three common service models are Infrastructure as a Service (IaaS), Platform as a Service (PaaS), and Software as a Service (SaaS).

These models give customers different levels of control over the technology they use. That difference also affects which parts of security belong to the cloud provider and which parts remain the customer's responsibility.

IaaS Infrastructure as a Service gives the customer more control over the systems running on the provider's infrastructure.
PaaS Platform as a Service gives developers a managed platform for building and running applications.
SaaS Software as a Service provides a completed application while the provider manages more of the underlying technology.
Key idea Moving to the cloud changes how security responsibilities are divided. It does not make those responsibilities disappear.

Sources used: NIST, The NIST Definition of Cloud Computing and Cloud Computing Synopsis and Recommendations.

02. Common Security Risks and Vulnerabilities

Security problems are not always caused by a major outside attack. Problems can also begin with weak access controls, incorrect settings, or other configuration mistakes.

This is why cloud security involves more than responding to hackers. Organizations also have to think about how their systems are designed, configured, and managed before a security problem happens.

A simple example

Imagine an organization stores files in a cloud service. The cloud provider's infrastructure may be secure, but the organization could still create a problem if a storage setting is configured incorrectly or if too many users are given access. In that situation, the risk comes from the way the service is being used rather than from the cloud provider's physical infrastructure. This is why access control and configuration need attention before an incident occurs.

Why this matters A weakness can already exist because of the way a system was configured or managed, even before anyone tries to attack it.

Sources used: OWASP Top 10: 2025 and CISA's Cloud Security Technical Reference Architecture.

03. Who Is Responsible for Cloud Security?

Using a cloud provider does not mean the provider handles every part of security. Cloud security uses a shared responsibility model, which divides responsibilities between the cloud provider and the customer.

AWS explains that the provider is responsible for the infrastructure its services run on, while customers are still responsible for areas such as their data, accounts, applications, and some of the security settings they choose.

Responsibility changes with the service

Microsoft Azure's shared responsibility guidance also shows that the customer's role changes depending on whether the service is IaaS, PaaS, or SaaS. As the provider manages more of the technology, the customer may manage less of the underlying system, but responsibilities involving data and accounts still remain important.

What this looks like in practice

With IaaS, a customer has more control over the systems running on the provider's infrastructure, which also means the customer has more security decisions to make. With SaaS, the provider manages more of the technology, but the customer still has to think about areas such as its users, accounts, permissions, and data. The exact dividing line changes, but shared responsibility is still present.

Remember this A secure cloud provider does not automatically mean everything a customer puts in the cloud is securely configured.

Sources used: AWS Shared Responsibility Model and Microsoft Azure Shared Responsibility in the Cloud.

04. Protecting Data and Access

Moving information to the cloud does not remove an organization's responsibility to think about how that information is protected. Organizations still need to consider who can access their data, how access is controlled, and what security and privacy decisions remain their responsibility.

Questions to keep in mind

  • Who should be able to access the information?
  • What permissions does each account actually need?
  • How is activity monitored for possible security problems?
  • How are data protection and privacy considered when the cloud environment is designed?

Protecting data and controlling access are closely connected. If access is not managed carefully, the information itself can become harder to protect.

This also means access decisions should not be treated as permanent. As people change roles or no longer need certain resources, organizations need to keep track of whether their permissions still make sense. Monitoring adds another part to this process because it can help an organization notice activity that may need to be investigated.

Sources used: NIST, Guidelines on Security and Privacy in Public Cloud Computing and Google Cloud's Security, Privacy, and Compliance Pillar.

05. Managing Cloud Security

Cloud security is an ongoing process rather than something an organization can set up once and forget about. Systems change, users are added, applications are updated, and new risks can appear over time.

The NIST Cybersecurity Framework 2.0 helps organizations organize cybersecurity risk management into different areas. This makes it easier to think about security before, during, and after a problem instead of treating cybersecurity as one single task.

The Cloud Controls Matrix takes a more cloud-specific approach by organizing controls across areas such as data security, identity and access management, infrastructure, logging, and incident management. Together, these frameworks show that cloud security depends on several areas working together.

Why organization matters

Without some kind of structure, it would be difficult to keep track of every part of a cloud environment that needs attention. A framework gives organizations a way to organize their security work, while a set of cloud-specific controls can help them look more closely at individual areas. This also reinforces an idea that appears throughout this guide: security has to be considered before a problem happens, but organizations also need a plan for monitoring and responding when something does go wrong.

Sources used: NIST Cybersecurity Framework (CSF) 2.0 and the Cloud Security Alliance Cloud Controls Matrix.

06. Reducing Mistakes Through Security Practices and Automation

Cloud environments can include many accounts, permissions, settings, services, and security controls. As an environment becomes larger, checking every setting manually can become difficult and mistakes can be easier to miss.

Security automation can help organizations apply controls and check whether they are being followed consistently. This can be especially useful for configuration problems, since a system can become vulnerable because of an incorrect setting even when no direct attack has happened.

Security benchmarks can add another layer of guidance. The CIS Amazon Web Services Foundations Benchmark, for example, provides practical recommendations for security settings in AWS. Frameworks, benchmarks, and automation serve different purposes, but they can work together to make cloud security more consistent.

Automation helps, but it does not make the decisions

Automation is useful for repetitive work, especially when the same controls or settings need to be checked across a larger environment. However, an organization still has to decide what should be protected, which controls make sense, and what should happen when a problem is found. In other words, automation can make security practices more consistent, but it does not replace the planning behind those practices.

Sources used: NIST Cloud Security Automation Framework and the CIS Amazon Web Services Foundations Benchmark.

Putting the Pieces Together

Looking across these different areas shows that cloud security is not one setting, tool, or person's responsibility. The service model affects responsibility, responsibility affects which controls the customer must manage, and those controls affect how well data, accounts, and applications are protected.

The same connection appears when looking at security mistakes. Access problems and misconfigurations can create weaknesses, while frameworks, benchmarks, monitoring, and automation can help organizations manage those weaknesses more consistently. None of these practices works as a complete solution by itself.
